# RCA — UnlockVault (mass-file-vault) Cloudflare 520 at origin

## Summary
The app is NOT down due to a boot crash or a missing secret. It is an **intermittent
availability failure**: the production backend periodically stops answering its health
endpoint in time, Kubernetes fails the **liveness probe**, kills and **restarts** the
container, and during each restart window the origin is unreachable — which Cloudflare
reports as **Error 520 (origin "Host" red X)**. The 520 you saw at **2026-10-03 23:13:32 UTC**
lines up with a container restart at **23:13:21 UTC**.

At the moment of this investigation the live URL is healthy again:
`GET /` → 200, `GET /api/` → 200 ("Mass File Unlocker API"), `GET /health` → 200 ("healthy").
So the symptom is recurring, not permanent.

## Evidence
1. **Pod events (run c80ddd09…):**
   - "Readiness probe failed: HTTP probe failed with statuscode: 503" ×43 (22:53–23:18 UTC)
   - "Liveness probe failed: HTTP probe failed with statuscode: 503" ×45
   - "Container … failed liveness probe, will be restarted"
   - restart_count = 3; last_termination = **Completed, exit 0, finished 23:13:21 UTC**
     (graceful SIGTERM from the liveness kill — **no OOMKilled**, so this is not a memory OOM).
2. **nginx error log (backend not responding to the probe):**
   `upstream timed out (110: Connection timed out) while reading response header from
   upstream, request: "GET /health", upstream: "http://127.0.0.1:8001/health"` — repeated
   23:18–23:20 UTC. The backend's worker was blocked and could not serve /health in time.
3. **Timeline correlation:** container restart 23:13:21 UTC ≈ Cloudflare 520 at 23:13:32 UTC.
4. **App is functionally up between restarts:** `/api/files`, `/api/unlock`,
   `/api/match-passwords`, `/api/download-zip`, `/api/delete-bulk` all logged **200 OK**.
5. **Secrets present & non-empty (active run):** MONGO_URL, DB_NAME, EMERGENT_LLM_KEY,
   INTEGRATION_PROXY_URL, CORS_ORIGINS, REACT_APP_BACKEND_URL. The 520 is **not** a
   missing/blank secret and **not** a failed object-storage init at boot (storage init is
   wrapped in try/except and startup completes — confirmed by the app serving traffic).
6. **Backend process is up and listening on 8001** (nginx successfully proxies /api/* to
   127.0.0.1:8001 and gets 200s; it only times out when the worker is busy).
7. **Tier_0 (Starter):** cpu 50m / cpu_limit 250m, memory 200Mi / memory_limit 512Mi,
   2 replicas, no HPA.

## Root cause
The backend runs a **single, synchronous-blocking request path**. The unlock/storage work
(`POST /api/unlock` → CPU-heavy PDF/Excel unlock + an object-storage `put_object` at
`server.py:61`) **blocks the uvicorn event loop/worker**. While that request is in flight the
server cannot answer the liveness/readiness probe on `/health`, so nginx returns a 5xx to the
probe ("upstream timed out"). Kubernetes counts the liveness failures, kills the container,
and restarts it. Each restart leaves the origin momentarily unreachable → **Cloudflare 520**.
The tier_0 **250m CPU cap** amplifies this: the CPU-heavy unlock saturates the small quota and
starves the probe, making the timeouts more frequent.

## Secondary issue (functional, not the 520)
`POST /api/unlock` intermittently fails because the object-storage PUT returns upstream 500:
`500 Server Error: Internal Server Error for url:
https://integrations.emergentagent.com/objstore/api/v1/storage/objects/mass-unlocker/…​.xlsx`
raised at `backend/server.py:61` (`put_object`) → `server.py:284` (`unlock`). EMERGENT_LLM_KEY
and INTEGRATION_PROXY_URL are present, so this is an upstream object-storage error (or an
unhandled failure in the upload path), not a missing credential. It surfaces as a 500 on
unlock, independent of the 520.

## Recommended fixes
### Code (E1 — requires redeploy)
- Move the CPU-heavy unlock + object-storage `put_object` work **off the event loop**: run it
  in a threadpool (`await asyncio.to_thread(...)` / `run_in_executor`) or a background task,
  and/or run uvicorn with multiple workers, so `/health` stays responsive during heavy
  requests. This is the primary fix that stops the liveness-kill restarts.
- Add a dedicated, lightweight **FastAPI `/health` route** that returns 200 without touching
  DB/storage (backend currently returns 404 for `GET /health` — seen in logs), so the probe
  never depends on request-handling capacity.
- Harden the `put_object` path in `/api/unlock`: catch the upstream 500 and return a clean,
  retryable error instead of an unhandled 500.

### User (Deployment Panel → Resources) — mitigation
- The tier_0 250m CPU cap worsens the probe starvation. After/with the code fix, consider
  upgrading the tier to give the unlock workload CPU headroom. (A tier bump alone will not
  fully fix a blocked event loop — the code change is the real fix.)

### Third party / support — if object-storage 500s persist
- If `/api/unlock` keeps getting 500s from `integrations.emergentagent.com/objstore` after the
  code hardening, raise it with Emergent support with a sample timestamp/object path, as the
  object-storage upstream itself is returning 500.
